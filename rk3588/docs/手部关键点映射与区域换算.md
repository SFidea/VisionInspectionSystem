## 〇、★ 关键勘察结论（2026-10-03，改写本文档的前提）

动手前先读了 Windows 版源码，**结论推翻了原本的悲观假设**：

### SOP 手部判定走的是 YOLO Pose，不是 MediaPipe

| 组件 | 实际角色 |
|---|---|
| `SOPModule._handPoseService` → `IHandPoseEstimationService` | **主路径**，产出 `HandPoseEstimationResult` |
| `YoloPoseHandEstimationService` | 实际推理实现，**基于 YOLO COCO Pose** |
| `HandPose` | 单只手：`TrackId` / `HandType` / `BoundingBox` / `Keypoints`（枚举型 `HandKeypointType`，**不认序号**） |
| `StepConditionEvaluator.CheckHandCondition` | 手部条件判定，**消费 `HandPose` 而非 MediaPipe 的 21 点数组** |
| `PoseConditionEvaluator` | 另一条并行路径（人体 `TrackedHuman` + `KeypointType.LeftWrist/RightWrist`），走 `SOPModule._poseEvaluator` |
| `MediaPipeHandDetector` | 第三条路径（手部特效/UI 用），**SOP 判定主链路不依赖它** |

**这意味着什么（好消息）**：

1. **路线 B 不是"从 MediaPipe 换成陌生模型"，而是"继续用 YOLO Pose 家族，只是换成 RKNN 板端实现"** → 关键点语义同源，风险大幅下降。
2. **Windows 版的 `HandKeypointType` 是枚举**（`Wrist` / `ThumbTip` / `IndexFingerTip` / …），**本来就不依赖 MediaPipe 的 21 点序号约定** → 我原先担心的"序号错位导致静默判错"风险**不存在**。
3. 配方 YAML 里的 `keypoints: required: [LeftWrist, RightWrist, Nose]` 属于 **`monitoring`（可视化/配置段）**，**不参与条件判定**，无需迁移适配。

### 仍需注意的两点

| # | 事项 | 说明 |
|---|---|---|
| 1 | **YOLO-pose 手部专项模型的 kpt 顺序** | 若沿用 `rknn_model_zoo` 的 COCO 17 点人体模型 → `LeftWrist`=15 / `RightWrist`=16（标准 COCO 顺序）。若用自训手部 21 点模型 → 顺序由自己定，**须与 Windows 版 `HandKeypointType` 枚举逐一对齐**（见第三节） |
| 2 | **两条手部路径并存** | `StepConditionEvaluator`（`HandPose`）与 `PoseConditionEvaluator`（人体 pose）都在跑。P1 移植时须确认**配方实际走哪条**——从 `SOPYamlConfig.cs:725-754` 看，`hand_in_region` 等方法会被转成 `ConditionType.HandInRegion` 等，走**第一条**（`StepConditionEvaluator`） |

## 一、为什么仍要做语义映射

即使 Windows 版用枚举，**跨模型边界的语义归一仍然必要**：

- Windows 版 `HandKeypointType` 枚举 ↔ RKNN 模型的 kpt 索引，二者需一张**显式对照表**。
- 没有这张表，将来若换模型（自训 21 点 vs 官方 COCO 17 点），改错一处就是**静默判错**：编译通过、运行不报错、条件永远不满足或永远满足。
- 语义层让**引擎与模型解耦**：换模型只改 `hand_kpt_map.cpp` 一个文件。

## 二、语义槽位表（引擎唯一契约）

引擎侧只依赖这 **10 个槽位**，定义在 `inference/include/detector.h`：

| `HandSlot` | 语义 | 对应 C# `HandKeypointType` | 主要被哪些 SOP 条件使用 |
|---|---|---|---|
| `kWrist` | 腕关节 | `Wrist` | `HandInRegion` / `HandStable` 基准 |
| `kThumbTip` | 拇指尖 | `ThumbTip` | `HandMoveFromTo` |
| `kIndexTip` | 食指尖 | `IndexFingerTip` | `HandMoveFromTo` / `HandNearObject` |
| `kMiddleTip` | 中指尖 | `MiddleFingerTip` | `HandMoveFromTo` |
| `kRingTip` | 无名指尖 | `RingFingerTip` | `HandMoveFromTo` |
| `kPinkyTip` | 小指尖 | `PinkyFingerTip` | `HandMoveFromTo` |
| `kIndexMcp` | 食指第二关节 | `IndexFingerPip`(推断) | `HandMoveFromTo` 起点、`HandStable` |
| `kPalmCenter` | 掌心 | （无对应，导出量） | `HandNearObject` |
| `kThumbIp` | 拇指第二关节 | `ThumbIp`(推断) | `HandStable`（捏取动作） |
| `kPinkyMcp` | 小指第二关节 | `PinkyFingerPip`(推断) | 手掌张开度判定（辅助） |

> C# 枚举的**精确成员名与是否覆盖全部 21 点**，P1 移植时以 `HandPoseEstimationModels.cs` 的 `HandKeypointType` 定义为准逐条抄入本表（标"推断"的需核实）。

## 四、坐标系与朝向差异

| 维度 | Windows 版（YOLO Pose） | RK3588（YOLOv8-pose RKNN） | 处置 |
|---|---|---|---|
| 坐标原点 | 左上角，像素 | 左上角，像素 | ✅ 一致 |
| x 向右 / y 向下 | 是 | 是 | ✅ 一致 |
| 点顺序 | 枚举 `HandKeypointType`，不认序号 | 由模型 label 决定 | ✅ 第三节映射表解决 |
| **左右手定义** | C# `HandType.Left/Right` | 模型可能不区分，输出顺序不保证 | ⚠️ 需在 backend 内几何归一化（见下） |
| 可见性置信度 | `HandKeypoint.Confidence` | `kpt score` | 阈值须与 C# 一致（记入台账阈值表） |

### 左右手归一化

**先核查再实现**：P1 移植时确认 5 个配方是否有条件**显式依赖左右手**。
从已看到的配方看，全部写的是 `hand: "any"` → **当前不依赖左右手**，
因此左右手归一化对现有 SOP 行为无影响，可作为 P2 的加固项而非阻塞项。

## 五、区域换算

### 现状核查结论（2026-10-03）

已 grep 5 个配方：**区域定义全部基于 `region:` 名称引用（`from_region` / `to_region` / `region`），
没有一处直接引用关键点索引**。区域本身的像素/归一化坐标定义在 YAML 的 `regions:` 段，与手部模型无关。

→ **区域不需换算、不需重标定。** 这条风险（原文档列为待核查项）已排除。

### 唯一需注意的点

`HandMoveFromTo` 判定"手是否在区域内"时，用的是**手部 bbox 中心**还是**腕关键点**？
P1 移植时从 `StepConditionEvaluator.CheckHandCondition` 逐行确认，
并在 C++ 侧**用完全相同的判定基准**（不要想当然改成 palm center）。

## 六、对拍口径（"100% 保留"如何验证）

路线 B 下推理后端换了（ONNX Runtime → RKNN），**浮点坐标不可能逐点相同**，
因此对拍基准**从坐标上移到行为**：

### `decisions.jsonl` 每帧必须记录（P0 数据集设计要求）

```json
{
  "frame": 1234,
  "ts_ms": 1234567,
  "step_id": "s2",
  "conditions": {
    "HandInRegion": true,
    "HandStable": false,
    "HandMoveFromTo": true,
    "HandNearObject": false,
    "ObjectInZone": true
  },
  "violations": [],
  "next_step": "s3"
}
```

### 验收标准（G4 主闸门）

| 指标 | 阈值 |
|---|---|
| 12 类条件**逐帧布尔结果**一致率 | ≥98% |
| **5 类手部条件**（`HandInRegion`/`HandNotInRegion`/`HandStable`/`HandMoveFromTo`/`HandNearObject`）一致率 | **100%** |
| 违规触发帧序号一致率 | 100% |

### 差异处置顺序（不得跳步）

1. 查 `hand_kpt_map.cpp` 映射表（最常见）
2. 查左右手归一化是否翻转
3. 查"手在区域内"的判定基准是否与 C# 一致（第五节）
4. 换精度档位 INT8 → FP16
5. 仍不一致 → **记入《配方差异表》（`移植台账.md` 第六节），由 Sir 裁决**，禁止私自调 `stable_frames`
