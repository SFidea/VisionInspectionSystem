## 〇、★ 关键勘察结论（2026-10-03 深挖，**修正了此前两轮的错误判断**）

> 本节经三轮源码勘察才收敛。前两轮结论均有偏差，以本节为准。

### 真实的手部检测链路（`YoloPoseHandEstimationService`，类名有误导性）

```
① YOLOv8-pose   —— 检测【人体】，取手腕关键点定位 → 裁剪出 224×224 手部图
② MediaPipe Landmark (hand_landmark_sparse_Nx3x224x224.onnx) —— 在裁剪图上出 21 点
③ 坐标反变换：224 归一化 → 乘 cropRect 宽高 → 加 cropRect 偏移 → 原图坐标
④ HandPose.Keypoints ← 21 个 HandKeypoint，置信度【硬编码 0.9f】
```

**所以：类名叫 `YoloPoseHandEstimationService`，但手部 21 点实际由 MediaPipe Landmark 产出，
YOLOv8-pose 只负责"找到手腕在哪"。MediaPipe 是真在主路径上的，我第一轮说的"并行路径"是错的。**

### 但路线 B 的技术判断依然成立（原因变了）

| 项 | 结论 |
|---|---|
| `HandKeypointType` 枚举 | **确实是枚举**（`Wrist=0` / `ThumbCMC=1` … `PinkyTip=20`，共 21 个），序号与 MediaPipe 标准一致 |
| 关键点置信度 | 硬编码 `0.9f`，**列表内恒定** → 过滤/不过滤等价 |
| 关键点数量 | `for (i = 0; i < landmarks.Count && i < 21; i++)` → **上限 21，实际可能少于 21** |
| ★ `GetCenter()` | **全部关键点算术平均，分母 = 实际点数** |
| 配方区域 | 全用 `region:` 名称引用，不引用关键点索引 → **不需重标定** |
| 配方左右手 | 全为 `hand:"any"` → **不显式依赖** |

**路线 B 之所以仍然可行**：`GetCenter()` 的分母是**实际返回点数**，而 RKNN 侧手部模型输出点数
可以做到**与 Windows 版实测一致**（只要 §五 的模型方案对齐）。这比"序号错位"是**小得多**的问题——
序号对齐只需一张映射表（§三），点数对齐只需模型选型（§五）。

### 仍是最高风险的两点

1. **点数不对齐 → `GetCenter()` 中心偏移** → `HandInRegion`/`HandStable` 判定改变（G4 必挂）。
2. **左右手并非完全无关**：`SelectHand` 先按 `HandSide` 找右手，取不到才回退任意手；
   而 `HandType` 由 `handType == HandType.Left ? 0 : 1` 决定，**依赖 palm 检测的左右手输出**。
   路线 B 必须复现这个左右手判定。

## 一、为什么仍要做语义映射

即使 Windows 版用枚举，**跨模型边界的语义归一仍然必要**：

- Windows 版 `HandKeypointType` 枚举 ↔ RKNN 模型的 kpt 索引，二者需一张**显式对照表**。
- 没有这张表，将来若换模型（自训 21 点 vs 官方 COCO 17 点），改错一处就是**静默判错**：编译通过、运行不报错、条件永远不满足或永远满足。
- 语义层让**引擎与模型解耦**：换模型只改 `hand_kpt_map.cpp` 一个文件。

## 五、区域换算与判定基准（★ 已于 2026-10-03 逐行查实）

### 结论：区域**不需换算、不需重标定**

已 grep 5 个配方：区域定义全部基于 `region:` 名称引用（`from_region` / `to_region` / `region`），
没有一处直接引用关键点索引。区域像素坐标定义在 YAML 的 `regions:` 段，与手部模型无关。

### ★★ 手部判定基准全表（C++ 侧必须 1:1 照抄，错一处 G4 对拍必挂）

这是 P1 移植最容易踩的坑——**没有一个条件是用"腕点"或"bbox 中心"判的，全部基于"关键点算术平均中心"**。

| 条件 | 判定基准 | 关键实现细节 |
|---|---|---|
| `HandInRegion` | `hand.GetCenter()` ∈ zoneRect | `zoneRect.Contains(center)` |
| `HandNotInRegion` | `!zoneRect.Contains(center)` | 取反 |
| `HandStable` | ① 中心须在 `zoneId` 区域内（若指定）；② `CenterHistory` 末 N 帧**最大相邻位移 ≤ Tolerance(默认 20px)** | 需先满足 `CenterHistory.Count >= StableFrames` |
| `HandMoveFromTo` | 主判据是**目标物体是否到达 to_region**；手中心仅作辅助 | 见下方详述 |
| `HandNearObject` | `IsHandHoldingObject` 三级判定 | 见下方详述 |

#### ① `GetCenter()` 的精确定义（最关键）

```csharp
// HandPoseEstimationModels.cs:108
public SKPoint GetCenter() {
    if (Keypoints.Count == 0) return new SKPoint(0, 0);
    float avgX = Keypoints.Average(k => k.X);   // ★ 全部关键点算术平均
    float avgY = Keypoints.Average(k => k.Y);
    return new SKPoint(avgX, avgY);
}
```

⚠️ **不是** bbox 中心、**不是** 腕关键点、**不是** palm center（MCP 均值）。

**对路线 B 的致命影响**：
`Keypoints` 是**列表**，平均值的分母 = 关键点**数量**。MediaPipe 固定 21 点，YOLO-pose 若只有 17 点或数量不同，
**中心的物理位置会系统性偏移** → `HandInRegion` / `HandStable` 判定结果改变。

**处置**（P2 必须做，二选一）：
- **方案甲（推荐）**：RKNN 侧手部模型输出**固定 21 点**且顺序与 Windows 版 `HandKeypointType` 枚举一一对应
  → `GetCenter()` 公式天然一致，无需补偿。
- **方案乙**：保留数量差异，但在 RKNN 侧输出前**补齐/裁剪到与 Windows 版相同的点集与点数**，
  或改用加权平均并把权重表记入《阈值对齐表》。**不得**直接用不同点数的平均值。

#### ② `SelectHand()` 的选手规则（含回退）

```csharp
// StepConditionEvaluator.cs:305
var preferredType = handSide switch { "left"/"左手" => HandType.Left, _ => HandType.Right };
var chosen = handResult.Hands.FirstOrDefault(h => h.HandType == preferredType && h.IsValidGesture(8))
          ?? handResult.Hands.FirstOrDefault(h => h.IsValidGesture(8));   // ★ 回退：任意一只
```
- `IsValidGesture(8)` = **至少 8 个关键点有效**。
- ⚠️ **即使配方写 `hand:"any"`，代码仍先取右手，取不到才回退**。所以左右手**并非完全无关**——
  当"只有一只手被检出"时，优先右手 vs 优先任意，会选到不同的手。**这是行为级差异高发点**，
  RKNN 侧的 `isLeft` 判定必须与 Windows 版 `YoloPoseHandEstimationService` 的左右手判定逻辑一致。

#### ③ `IsHandHoldingObject` 三级判定（任一命中即 true）

```csharp
// StepConditionEvaluator.cs:601，按顺序短路
1. hand.BoundingBox.IntersectsWith(objBox)                    // 手框与物框相交
2. objBox.Contains(hand.GetCenter())                          // 手中心在物框内
3. objBox.Expand(margin: 30f).Contains(hand.GetCenter())      // 手中心在物框外扩 30px 内
```
⚠️ 30px 是**固定像素常数**，不同分辨率下物理含义不同。C++ 侧照抄 30（不改成比例），
若板端相机分辨率与 Windows 版不同，**必须记入《配方差异表》**由 Sir 裁决。

#### ④ `IsInZone`（物体侧，与手部无关但常被混用）

```csharp
// StepConditionEvaluator.cs:848
return objectBox.IntersectsWith(zoneBox);   // ★ 只要有重叠即命中，不要求中心在区域内
```
物体判定用**矩形相交**，手部判定用**中心点包含**。两者语义不同，**不可混用**。

#### ⑤ `HandMoveFromTo` 的 `visitedFrom` 特殊逻辑（喝水配方的命门）

```csharp
// 手访问过 from_region  或  物体访问过 from_region，都算 visitedFrom
bool visitedFromByHand   = track.RecentRegions.Contains(fromRegion);
bool visitedFromByObject = _objectVisitedRegions[TargetObject].Contains(fromRegion);
bool visitedFrom = hasFrom && (ignoreFromRegion || visitedFromByHand || visitedFromByObject);
```
- 喝水配方的 `mouth_region` 场景：**手轨迹里可能根本没有 mouth_region**，
  必须靠**物体**（杯子）的区域访问记录，否则"放回"步骤会永远卡在 `visitedFrom=false`。
- ⚠️ 跳步检测时 `ignoreFromRegion=true` 放松此约束（否则跳步会漏报）。
- 移植时 `_objectVisitedRegions` 这张**跨步骤累积状态**必须一并移植，漏了会连锁失败。

## 五·补、跟踪状态（跨帧累积，移植时不可漏）

`_handTracks`（`HandTrackState`）需要跨帧累积两个历史量：

| 字段 | 用途 | 维护方式 |
|---|---|---|
| `CenterHistory` | `HandStable` 算位移 | 每帧 `Add(center)`，超过 `MaxHistory` 移除最旧 |
| `RecentRegions` | `HandMoveFromTo` 的 `visitedFromByHand` | 记录该手近期访问过的区域名 |

`ResetStableCounts()` 挂在状态机 `Start()` / `Reset()`；**移植时须一并移植这两张表的清理逻辑**，
否则复位后残留历史会污染下一轮的 `HandStable` 判定。
